# M2: Walking the Town, Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put roads on a 2-square road grid, then let the princess walk the town (keyboard, controller, mouse, touch) among seven wandering, chatting people she can talk to.

**Architecture:** Everything that moves lives in `src/sim/`. That covers the princess, the people, routes, chats and the open dialogue. The sim advances in fixed 1/60 s steps through `game.advance(seconds)`, using the seeded RNG. `render/` draws paper cut-out figures from art IDs and reads the sim state each frame. `ui/` turns keys, gamepad, clicks and taps into sim commands, and draws the dialogue box and chat bubbles as HTML over the canvas. Roads stay stored as squares in `world.roads`, but every rule and command works on whole 2×2 road cells.

**Tech Stack:** TypeScript (strict), Vite 8, Vitest 5, three@0.186.1, Gamepad API.

**Spec:** `docs/superpowers/specs/2026-11-16-m2-walking-the-town-design.md` (approved 2026-11-16). Mockups: `docs/design/m2-mockups/`.

## Global Constraints

- `src/sim/` is pure: no DOM, no `Math.random()`, seeded RNG only (`sim/rng.ts`). Same seed and same commands give the same game.
- `render/` and `ui/` read sim state and call `game.command(...)` / `game.advance(...)`. They never change state directly.
- Every tunable number goes in `src/data/balance.json`, and every name and line in `src/data/*.json`. Keys go in `data/keybindings.json`, gamepad buttons in `data/gamepad.json`.
- `game.command()` never throws. Bad input returns `{ ok: false, error }` and changes nothing.
- Names, art and text are original. Never use an em dash in player-facing text.
- No on-screen key hints.
- People stand 0.55 of a square tall, and the cottage wall is 1.0.
- Rigid movement: full speed the moment input is held, and zero the moment it is released.
- The princess never ends up outside the walls or inside a building.
- Works at 844×390 and 1280×800 with no console errors.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Never push without asking.

## Review Focus

1. **Big time steps.** `advance(5)` while she holds into a wall or gate (a background tab, or the debug hook) must still leave her inside the town. Pinned in Task 6.
2. **Building on her.** A cottage placed on the square she's standing on goes ahead, and she lands on its door road, never inside. Pinned in Task 10.
3. **Removing road under walkers.** Removing a road cell that a walker is on, or routing through, sends them back onto walkable cells within a few seconds. No walker stays on grass or keeps a route through the removed cell. Pinned in Task 8.
4. **More homes than people.** Extra cottages stay empty. Placing a home with nobody homeless changes nobody's home. Pinned in Task 8.
5. **Determinism.** Two games with the same seed and the same command and advance sequence give identical people and princess state after 60 s. Pinned in Task 10.

### Task 5: Pathfinding

**Files:** Create `src/sim/route.ts`. Test `tests/sim/route.test.ts`.

**Interfaces:**
- Consumes: `Cell`, `cellKey`, `cellOf`, `cellSquares` and `cellCenter` (Task 1).
- Produces:
  - `walkableCells(town: Town, world: World): Set<string>`: the cell keys of laid road cells, plaza cells, forecourt cells and the current stage's gate cells.
  - `findRoute(walkable: ReadonlySet<string>, from: Cell, to: Cell): Cell[] | null`: the route includes `from` and `to`. It's Dijkstra with a cost of 1 per side-by-side step. Ties are broken by neighbour order: east, west, south, north (`[1,0],[-1,0],[0,1],[0,-1]`). It returns `[from]` when `from` equals `to`, and `null` when either end is not walkable or there is no route.
  - `laneWaypoints(map: TownMap, route: Cell[], offset: number): { x: number; z: number }[]`: one point per cell, at the cell centre plus a lane shift. A direction `d` has the right-hand normal `r(d) = (-d.z, d.x)`. With `d_in` as the step into the cell and `d_out` as the step out of it:
    - when only one exists, or both are equal: shift by `r * offset`
    - otherwise: shift by `(r(d_in) + r(d_out)) * offset`
    - a single-cell route: the centre itself

**Files:**

**Interfaces:**
- Consumes: `kindAt`, `footprint`, `Town`, `World`.
- Produces:
  - `interface Princess { x: number; z: number; facing: { x: number; z: number }; sprinting: boolean; height: number; route: { x: number; z: number }[] }`
  - `interface WalkInput { x: number; z: number; sprint: boolean }`, where `x, z` is a ground direction of length 0 or 1
  - `World.princess: Princess`, which starts at `map.princessStart`, faces `{0, 1}` and is not sprinting
  - `World.walkInput: WalkInput`
  - `isSolidSquare(town, world, x: number, z: number): boolean`: true for `wall` and `outside` squares and for squares under a building
  - `moveCircle(town, world, at: {x,z}, delta: {x,z}, radius: number): {x,z}`: moves along x first, then z. On each axis it stops at the edge of any solid square or the statue box the circle would overlap, so sliding falls out of the per-axis split. The statue box is `statue ± 0.35`; the quest board box is `questBoard.x ± 0.45, questBoard.z ± 0.2`.
  - `stepPrincess(town, world, dt: number): void`:
    - Movement and sprint:
      - When the input is non-zero, she moves at `speed × dt` along the input, clears `route`, sets `facing`, and sets `sprinting` from `input.sprint`.
      - When the input is zero and she has a route, she walks toward `route[0]` at the walk speed, or the sprint speed when sprint is held, and drops the waypoint once she is within 0.05.
      - Otherwise she doesn't move, and `sprinting` becomes false.
    - Height:
      - `height = sprinting ? hoverHeight : 0`; render smooths it.
