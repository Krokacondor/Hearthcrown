# M1 Map & Placement Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The diorama shows the walled starting town (walls, three gatehouses, plaza with the statue, the castle with the quest board in front, the citizens' roads), and the player can lay roads and place papercraft buildings on an open grid through a Build menu, under rules that never strand anything.

**Architecture:** All rules live in pure `src/sim/` modules: the town map loader, building footprints, and the placement and road-removal rules, driven through `game.command()`. `src/render/` draws the town from the map and the world state through an art registry with packs and code fallbacks. `src/ui/` holds pure build-mode input logic (tested) and the Build menu; `main.ts` wires input to sim commands.

**Tech Stack:** TypeScript strict, Vite 8, Vitest 5, three 0.186.1 (pinned). No new dependencies.

**Spec:** `docs/superpowers/specs/2026-11-15-m1-map-placement-design.md` (approved 2026-11-15). Also PLAN.md 2.1, 2.2, 5.1 and DESIGN.md.

## Global Constraints

- `src/sim/` stays pure: no DOM, no `Math.random`, no `three`, `render/` or `ui/` imports (the architecture test enforces it).
- All content and tunable numbers go in `src/data/*.json`. Art is referenced by ID only; nothing outside `src/render/art/` knows how a piece is drawn.
- `game.command()` never throws; bad input returns `{ ok: false, error }` and changes nothing.
- Every action works with keyboard alone, mouse, and touch. Camera turning is PC-only and nothing may need it.
- Layouts work at 1280×800 and 844×390. UI follows DESIGN.md (Toy Theatre); marigold stays reserved for focus and "right now".
- Player-facing text: original, plain, no em dashes.
- Branch `m1-map`. Small commits ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Never push without asking.

## Decisions this plan makes (left to the builder by the spec)

- **Grid scale:** one grid square = one world unit (M0's ground tile). The board stays 40×32 squares. Building models are sized in squares; heights are tuned in the visual check (Task 8). The camera start target moves to the plaza.
- **Board size moves** from `balance.json` `map` into `map.json`; `balance.map` is deleted.
- **Coordinates:** square `(x, z)` covers world `[x, x+1] × [z, z+1]`; +x is east, +z is south; north is the top of town.
- **Facing:** `rot` 0..3, turning clockwise seen from above. A building's door faces south at rot 0, west at 1, north at 2, east at 3.
- **Starting town layout** (all inclusive ranges):
  - board 40×32
  - wall ring x 4..35, z 3..28 (inside: x 5..34, z 4..27)
  - gates: west (4,16), south (19,28), east (35,16)
  - plaza x 17..22, z 13..18, statue at world (20,16)
  - castle grounds x 17..22, z 4..7, and the castle (6×4, door squares 2 and 3) placed at (17,4) rot 0, so its door faces (19,8) and (20,8)
  - quest board on square (21,8)
  - cobbled roads: west z 16, x 5..16; east z 16, x 23..34; south x 19, z 19..27; north x 19, z 8..12 (38 squares)
  - dirt roads outside (scenery): west z 16, x 0..3; east z 16, x 36..39; south x 19, z 29..31
- **Plaza and gate squares are permanent road**: they count for doors and the network, and are never in `world.roads` and never removable.
- **Phone camera:** after a touch tap moves the highlight (the first tap), the camera eases to the highlight once the finger lifts. It never moves while a finger is down. This is how phone players reach the rest of the town without a keyboard.
- **Fading** applies to buildings, walls and gatehouses between the camera and the highlight.
- **Build menu key:** B. Turn key: R.

## Review Focus

1. **Fast mouse or finger drags while painting roads** skip squares between pointer events. The stroke must fill the gap so the road stays connected. Test in Task 9 (`strokeSquares`).
2. **Debug and console commands with odd coordinates** (fractional, negative, NaN, off the board, rot 4 or -1, unknown type, the castle type): `ok: false`, no throw, nothing changes. Test in Task 5.
3. **Turning a building next to the wall** so its turned footprint or door pokes past the wall: refused as outside, never placed half in the wall. Test in Task 3.
4. **A painted stroke that crosses a blocked square** (a building, a wall): the blocked square is skipped, and later squares still connect only if they touch the network. No floating pieces. Test in Task 5.
5. **Bad data files** (a gate not on the wall, the plaza outside the walls, a door index past the building's width, a missing field): loading fails at startup with a message naming the file and field, instead of drawing a wrong town. Tests in Tasks 2 and 3.
